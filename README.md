# streamdeck-orca

Stream Deck + から Orca を操作するプラグイン。

## 開発環境のセットアップ

Node.js 22.12.0 以上と npm、Git が必要です。リポジトリのルートで実行してください。

```sh
npm ci
git config --local core.hooksPath .githooks
```

`core.hooksPath` はクローンごとの設定です。新しくクローンした場合も上記のコマンドを実行してください。
設定は `git config --get core.hooksPath` で確認できます。

## レビュー依頼されたPRからAIを起動する

「Orca → レビュー依頼からAI起動」をダイヤルに配置します。操作IDやPRごとの割り当ては不要です。

1. `gh auth login --hostname github.com` でGitHub CLIにログインし、OrcaのCLIを有効にします。`gh`・`git` がPATH上に必要です（macOSはHomebrewの標準配置も探します）。
2. 設定画面で「自分への直接の依頼」または「自分の所属チームへの依頼」、起動するAI（Codex / Claude Code）、AIに渡すテキストを設定して保存します。
3. ダイヤルを回してPRを選びます。LCDにリポジトリ、省略したタイトル、PR番号、識別補助タグ、入力のみ/Enterありを表示します。完全な情報は設定画面で確認できます。
4. 押すと対象ブランチの既存ワークスペースを再利用し、なければPRのheadコミットから作成して、新しいAIを起動します。「入力後にEnterを送る」がオフなら下書きとして入力し、オンなら送信します。初期値はオフです。既存のAIへ追加入力する機能ではありません。
5. LCDをタップすると一覧を更新します。表示中は約30秒ごとに自動更新し、最新更新順で最大100件を取得します。取得上限・一部結果は件数の `+` と設定画面に表示します。

テキストには `{{pr_url}}`、`{{pr_number}}`、`{{repo}}`、`{{branch}}`、`{{head_sha}}`、`{{base_branch}}` を使えます。置換後1〜16000文字です。設定の編集や保存、候補の回転、一覧更新だけではAIを起動しません。

個人宛ては `user-review-requested:@me`、チーム宛ては `team-review-requested-user:@me` で検索します。一般の `review-requested:@me` はチーム依頼も含むため使用しません。[GitHubの検索仕様](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests#search-by-pull-request-review-status-and-reviewer)に従い、押下時にも認証アカウント・依頼・PRの状態を照合します。

GitHub.comとローカルOrcaが対象です。対象リポジトリがOrcaに未登録なら `~/orca/review-repositories/<owner>/<repo>` に取得して登録します。同じリポジトリが複数登録されている場合は起動を止めます。通常のPRはheadブランチを使い、forkのPRは本体側の同名ブランチとの混同を避けて `streamdeck-review/pr-<番号>` を使います。既存WSのHEADがPRと違う場合や未コミット変更がある場合は、自動更新・上書きせず理由を設定画面に表示します。新規WSのセットアップスクリプトは実行しません。

同じアカウント・PR・コミットの連打や複数ダイヤルからの操作で、AIを重複起動しません。起動済みの同じコミットを押すとWSを開き、再入力はしません。起動結果が不明の場合は自動再実行せず、元のPRと操作IDを記録します。Orcaで状況を確認したあと、設定画面の「同じPRでAIを起動し直す」から表示した一件の起動記録を解除できます。解除だけではAIは起動しません。

入力・下書きの引き渡しは、レビュー処理の開始・完了やGitHubへのレビュー投稿を意味しません。GitHubへのレビュー投稿はこのアクションから行いません。Enterなしの起動にはCLIに未公開のOrca認証済みローカル `agent.launchReplay` APIのdraft指定を使い、対応capabilityのないOrcaでは起動を拒否します。Windows・実機でのPRレビュー起動は未検証です。

## 入力待ち・返答の確認先を一押しで開く

「Orca → 確認先を開く」をキーに一つ配置してください。操作IDや個別ワークスペースの設定は不要です。OrcaのCLIと状態通知フックは有効にしてください。

- キーには次に開く対象、入力待ち/返答候補の理由、取得範囲の候補件数を表示します。長い名前は先頭と末尾を残して省略し、プロジェクトの略記と短い識別子を添えます。設定画面で完全名とパスを確認できます。
- 押すと表示していた作業場所を最新状態で照合して開き、次の候補へ進みます。初回は入力待ち優先、その後は返答候補も含めて一巡します。進行中と返答済みのAIが同居するワークスペースも返答候補に含めます。新しいワークスペースは自動追加します。
- 件数はワークスペース単位で、待ちと返答の同居は入力待ち1件として数えます。**未読数や残タスク数ではありません。開いても件数を減らさず、既読・承認・対応済みにはしません。** 状態が続けば一巡後に再び表示します。入力待ちには親AIへの待ちも含まれ得ます。
- 対象が消失したり状態・実行環境が変わった場合は、その押下で別候補を開きません。新表示を確認して再度押してください。候補なしの押下は再取得のみです。長押しに追加操作はなく、要求中の連打は溜めません。
- 「一部取得」「一部不明」は全体を確認できていない表示です。接続失敗をゼロ件や完了として扱いません。該当ペインを特定できない場合はワークスペースまで開くため、入力先はOrcaで確認してください。

既存の操作IDの選択は変更しません。たとえばこのキーでBを開いても、Aを選択中の「コマンド・AI指示」キーはAが対象のままです。「表示AIへ入力」はキーに表示済みのAIが対象です。どちらも別途キーを押す必要があり、この確認先キーから入力・承認・コマンド実行は行いません。巡回位置と移動結果は再起動時にリセットされます。

調査と採用理由は [AI駆動開発の課題](docs/research/ai-development.md)、[設計](docs/design/attention-workflow.md) を参照してください。コードの正しさや仕事全体の完了は判定しません。

## ワークスペースの状態を表示する

「Orca → ワークスペースの状態」を液晶ボタンに配置します。Orca のCLIとエージェントの状態通知フックを有効にしてください。各ボタンが割当先WSを直接保存し、ダイヤルなしで使えます。

1. Orca の画面で登録したいWSを選び、ボタンを **700ms長押し** します。成立時点の選択WSを取得し、保存を読み戻して確認してから「登録完了」を表示します。ファイル・ブラウザー・ネイティブChat表示中や、AI・ターミナルがないWSも登録できます。登録では画面移動やAI入力を行いません。
2. **短押し** で割当先WSへ移動します。ダブル操作との判別のため、**指を離してから500ms待ちます**。入力待ちターミナルを優先し、対応するターミナルがなければWS自体を選択します。
3. **ダブル**（一度離してから500ms以内に二度目を押し、離す）で、割当先WSのGitHub Issue / PRを既定ブラウザーに開きます。二押目を700ms長押しした場合は登録だけを行います。

登録・再割当のたびに設定画面を開く必要はありません。同じWSを複数ボタンへ登録しても独立しています。一つを再割当しても、他のボタンやコマンドキーの対象は変わりません。未割当には「長押しで登録」を表示し、先頭WSを自動登録しません。割当済みWSが削除・再作成された場合は、長押しで登録し直してください。

関連先は Orca 1.4.254 で確認した `reference list --worktree id:<割当WS>` の保存済み参照から取得します。Orca の明示的な選択中参照を優先し、指定がなければPR、次にIssueを使います。同じ優先順位で複数ある場合は設定画面から選び、ボタンとWSの組に保存してください。GitHub.comのIssue / PRが対象です。関連先なし・保存した参照の消失・未対応の選択中参照・取得失敗では理由を表示し、別リンクへ振り替えません。別WSへの再割当で以前の関連先選択は破棄します。

ボタン設定に旧操作IDが保存されている場合は、そのWSを各ボタンへ一度だけ引き継ぎ、その後は個別設定を復元します。旧版で既定IDを一度も保存していない空設定は、新規ボタンと区別できないため未割当とし、長押しで登録してください。操作IDの入力やダイヤルとの連動は状態ボタンからなくなりました。「ワークスペース切り替え」ダイヤルは削除しました。コマンド・AI指示キーと並列変更レーダーは、操作IDごとの保存済み対象を維持します。保存のない新規IDでは従来どおり一覧の先頭を初期対象にするので、実行前に表示を確認してください。今回、新たな対象変更UIは追加していません。

キーはWS名を2行で表示し、プロジェクト略記・短タグ・進行状況を添えます。進行中は青い背景のインジケーターが動き、入力待ち・返答あり・待機・状態不明を区別します。長押し中、取得・保存中、登録完了、未割当、関連先なし、複数候補、選択先消失、取得失敗もキーに表示し、詳細理由は設定画面で確認できます。短タグは一意なIDではありません。同じ省略名・プロジェクト略記・短タグが重なると操作を止め、設定画面の完全IDとパスで照合を促します。

状態は約2秒ごとに更新します。取得失敗や対象消失では以前の進行中表示を残しません。ページ切替では最後の正常取得から5秒未満の表示を再取得中だけ利用します。設定変更・ページ離脱・切断・実行環境変更で保留操作を取り消し、遅い応答から別WSへ差し替えたり、処理中の連打を後で実行したりしません。保存できない場合は元の割当を復元し、復元まで確認できなければ「保存結果不明」として設定の開き直しを求めます。

画面選択は `worktree ps` の `isActive` を利用します。CLIを実行するディレクトリやAIペインの選択は使いません。登録直前にも選択WS・runtimeId・WSの実体を再照合します。ローカルOrcaのWSが登録対象です。既存のAI入力アクションは引き続きAIターミナル・ペインを厳密に検証します。

CLI は環境変数 `ORCA_CLI_COMMAND`、PATH、macOS の `/opt/homebrew/bin`・`/usr/local/bin` から実行前に選びます。接続失敗で別ビルドへ切り替えません。ターミナルなしのWS移動は既存の認証済みローカルRPC `worktree.activate` を利用します。実機キーの操作感・物理画面の描画・実Orcaでの登録と移動・既定ブラウザー起動は未検証です。SDKへの画像送信完了は実機描画完了の保証ではありません。

## コマンドを実行・AIへ指示を送る

1. 「Orca → コマンド・AI指示」をキーに配置し、保存済みの対象に対応する操作 ID を設定します。対象はキーと設定画面で確認してください。
2. 実行モード、ボタンの表示名、実行内容を入力して「保存」を押します。設定を保存しただけでは実行しません。
3. 実機のキーを押すと、同じ操作 ID で選択しているワークスペースに対して一度だけ実行・送信します。設定変更直後など、キー表示の更新を確認できない間は実行しません。

- **シェルコマンド**：`npm test` などを、そのワークスペースの新しい実行用ターミナルで起動して表示します。Orca が起動するシェルの文法で入力してください。既存の AI 端末へのコマンド入力は行いません。
- **AIへの指示**：「今回の変更をレビューして」などを、Orca CLI が認識するターミナル上の AI へ送ります。「AIが1つなら自動選択」は、送信可能な AI が1つの場合だけ送信します。複数いる場合は設定画面の送信先から選んでください。

シェルには「終了時にターミナルを閉じる（成功・失敗とも）」と「正常終了時だけターミナルを閉じる」の二つのチェック項目があります。既定は両方オフです。前者がオンなら終了コードにかかわらず閉じ、後者だけオンなら終了コード 0 の場合だけ閉じます。両方オンなら前者と同じ動きです。

自動クローズは macOS / Linux の `sh` と環境変数 `$SHELL` のシェル（未設定なら `/bin/sh`）で実行します。実行内容は別のシェルプロセスで動かすため、`exit` も含めて終了コードを取得できます。バックグラウンドへ切り離した処理ではなく、登録したスクリプト自体の終了を判定します。プラグインの稼働中に終了を監視し、この実行で作ったターミナルだけを閉じます。Orca やプラグインの再起動、端末の再作成、通信切断などで終了や対象を確認できない場合は自動では閉じません。直近の実行欄で終了コードと自動クローズの結果を確認できます。

指定した AI の送信先はワークスペースごとに保存します。送信時にワークスペース・runtimeId・端末の識別子・AIの種類を確認し、端末の再作成や種類の変更を検知した場合は送信せず選び直しを求めます。同じ端末内で同じ種類の AI が別の会話を始めたかは判別しません。AI がいない場合に新しい AI を起動することはありません。ネイティブ Chat への指示送信は対象外です。

ボタンは要求中の連打をまとめ、取得途中に設定や対象が変わった場合は実行前に中止します。「受付済み」はコマンドや指示の受付であり、処理の完了・テスト成功を表しません。AI の処理開始が確認できた場合は、設定画面の直近の結果に表示します。結果不明の場合は自動で再実行・再送信せず、設定画面に元のワークスペース名と結果を残します。実際の出力は Orca で確認してください。

## 並列変更レーダー

別々のワークスペースで、共通するファイルや行域を変更している接点を手元で探せます。

1. 新しい「Orca → 並列変更レーダー」をダイヤルに配置します。
2. 保存済みの対象に対応する操作 ID を設定します。既定は `main` です。
3. レーダーはその操作 ID の保存済みWSを自分側として、同じGit作業系列の別WSを自動比較します。
4. レーダーを回して接点を選び、押すと自分側、画面をタップすると相手側のコードを開きます。ステージだけの接点はステージ差分、削除・リンクや比較元を直接表示できない場合は、その側のWSを開きます。

LCDは「同じ行域」「同じファイル」「内容が同じ」「追加・削除」「手動で確認」を区別します。短い名前と両WSの短タグ、ファイルの短タグを表示し、設定画面で完全な名前・パス・ID・共通基点・開く行を照合できます。表示が重複して識別できない場合はOrca側で開いてください。

比較は両HEADの共通祖先を基点に、コミット済み・ステージ済み・作業ファイルの変更を含めます。Gitで無視されていない未追跡ファイルの同path追加も対象です。約8秒ごとに更新し、開く直前にも対象と内容を照合します。内容が変わった場合は自動で別の接点を開かず、更新後に押し直します。

「同じ行域」は共通基点の変更行域が重なるという情報であり、実際のマージ競合の確定ではありません。「共通ファイルなし」もmergeの安全や品質を保証しません。異なるファイル間の依存は検出しません。ソース編集・AI送信・merge・stage・commitは行いません。

ローカルGitの同じ `git-common-dir` を持つWSが対象です。外部Git filter設定のあるrepo、別clone、remote、Gitルート外、リンク経由のpath、共通基点を一つに決められない場合等は対象外・未比較になります。比較は最大12WS、一覧確認24WS、1組の共通ファイル32件、通常ファイル2MB、Git出力1MBを上限とし、取得時間にも上限があります。一部を取得できなかった場合はLCDに「一部」や「未比較あり」、設定画面に理由を出します。Windowsの実環境は未検証です。

## キーに表示した AI に文字列を入力する

1. 「Orca → 表示AIへ入力」をキーに配置します。操作 ID やダイヤルは不要です。
2. 本文・表示名を設定し、必要な場合だけ「Enterも送る」をオンにします。
3. 「表示先を確認して入力する動作を有効にする」にチェックして保存します。以前の「アクティブAIに入力」も本文・Enter設定を保持しますが、この確認保存まで入力しません。保存自体は入力しません。
4. Orca でAIターミナルを選び、キーに出るワークスペースとAI種別・端末位置を確認してから押します。

保存選択を約2秒ごとに読み、表示候補として使います。現在のGUI選択と一致する保証はありません。押すと表示済みのAIを固定し、完全なワークスペース・端末handle・incarnation・ペイン・端末レイアウトを再照合します。別のAIへ振り替えません。画像の更新中、ページ復帰のキャッシュ表示中、切断や端末再作成・レイアウト変更があれば入力を拒否します。更新完了だけで入力せず、改めて押す必要があります。

キー上段の「入力のみ」「入力＋Enter」は受付結果と別に表示します。端末位置の T1 などは端末レイアウト内のタブ順です。ファイル・ブラウザを含む全タブ番号ではありません。左右上下はOrcaが返す端末一覧の構造を表し、設定画面で完全なAI名・パス・ID・位置を照合できます。返却された位置は省略せず、複雑でキーに収まらない配置では入力しません。停止・未接続のペインやグループが省かれ、画面配置と異なる場合があります。同名AIを見分けられないときはキーを押さず、Orca側で入力してください。

既存の入力は消さず追加入力します。Enterオンなら既存入力も含めて送信します。オフの複数行・Tabは bracketed paste で渡すため、AI側の対応が必要です。「受付済み」は処理完了ではありません。設定画面の直近1件には押下時の宛先・表示名・Enter有無・時刻・結果を保持し、設定変更やページ復帰でも残します。本文は履歴へ複製せず、記録はプラグイン終了で消えます。記録なしは過去の未入力を意味しません。結果不明でも自動再送しません。

macOS / Linux のローカルAIターミナルが対象です。macOS標準の `/usr/bin/sqlite3`、LinuxはPATH上の `sqlite3` を使い、Orca 1.4.229のアクティブプロファイルを読み取り専用で参照します。Windows・ネイティブChat・リモート環境は対象外です。同じ端末プロセス内での会話入替までは識別できません。

## プラグインのビルドとインストール

Stream Deck アプリ 6.9 以上と Stream Deck + が必要です。キーとダイヤルに対応しています。
SDK は `@elgato/streamdeck` 2.1.2、プラグイン内の実行環境は Node.js 20 を使用しています。

```sh
npm run build
npm run validate
npm run link
npm run restart
```

Stream Deck アプリのアクション一覧から「Orca → ワークスペースの状態」をキーに配置し、OrcaでWSを選んで長押し登録してください。コマンドキー・レーダーは、設定画面で指定した操作IDの保存済み対象を使います。WS選択ダイヤルはありません。

`link` は開発用にこのリポジトリの `.sdPlugin` ディレクトリを Stream Deck にリンクします。

インストール用ファイルを作る場合は `npm run pack` を実行します。`dist/` に生成された `.streamDeckPlugin` ファイルをダブルクリックしてインストールできます。

- `src/plugin.ts`: SDK 接続とアクション登録。
- `src/actions/workspace-status.ts`: WS状態キーの操作。
- `com.tanaka-takuto.orca.sdPlugin/manifest.json`: プラグインの定義。
- `com.tanaka-takuto.orca.sdPlugin/imgs/`: Elgato CLI 付属のテンプレート画像。

SDK と開発用 CLI はプロジェクトの依存としてインストールしているため、グローバルインストールは不要です。
参考: [公式 SDK ドキュメント](https://docs.elgato.com/streamdeck/sdk/v2/guides/keys/)、[公式 CLI ドキュメント](https://docs.elgato.com/streamdeck/cli/commands/link/)。

## 保存時に自動反映する開発モード

初回のみ `npm run build` と `npm run link` を実行してください。`.streamDeckPlugin` ファイルから通常インストールした Orca がある場合は、先に Stream Deck アプリで Orca をアンインストールしてからリンクします。他のプラグインは操作しません。必要に応じて Orca のアクションを配置し直してください。

```sh
npm run dev
```

このコマンドを起動したまま `src/` を保存すると、自動ビルド後に Orca プラグインだけを再起動して反映します。manifest・画像・UI の変更も監視します。pack や再インストールは不要です。再起動時にはプラグインのメモリ上の状態がリセットされます。

ビルドと公式 CLI の検証が成功した場合だけ再起動します。構文エラーや不正な manifest がある場合は再起動せず、修正して保存すると再開します。型チェックは `npm run typecheck` で実行します。終了は `Ctrl+C` です。

開発用リンクを確認できない場合、`dev` は理由を表示して終了します。通常インストールしたコピーを誤って再起動して、変更が反映されたように見せることを防ぎます。

## Git フック

フックは `.githooks/` で管理します。

- `pre-commit`: `npm run lint` でプロジェクト全体の JavaScript・TypeScript・JSON などを Biome で lint・整形チェックします。エラーがある場合はコミットを拒否します。ステージしていない変更もチェック対象です。
- `commit-msg`: 自作の `.githooks/check-commit-message.mjs` で先頭行が [Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) 形式かを検証し、不正なメッセージを拒否します。検証スクリプトは Node.js の標準機能のみを使用し、commitlint などの追加ツールは使いません。

コミットメッセージの形式は `type(scope): 説明` です。`scope` は省略できます。破壊的変更は `feat(api)!: 説明` のように `!` を付けて示せます。

```text
feat: Orca のワークツリーを切り替えるアクションを追加
fix(dial): ダイヤルの回転方向を修正
chore: Git フックを設定
```

使用できる type は `build`、`chore`、`ci`、`docs`、`feat`、`fix`、`perf`、`refactor`、`revert`、`style`、`test` です。
type は小文字で指定し、コロンの後には半角スペースと空でない説明を書いてください。本文・フッターは検証対象外です。

## チェックと修正

```sh
npm run lint
npm run lint:fix
npm test
```

`lint:fix` は安全に自動修正できる lint エラーと整形を修正します。変更内容を確認し、`git add` してからコミットしてください。
