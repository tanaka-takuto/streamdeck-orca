# streamdeck-orca

Stream Deck + から Orca を操作するプラグイン。

## 開発環境のセットアップ

Node.js 22.12.0 以上と npm、Git が必要です。リポジトリのルートで実行してください。

```sh
npm ci
git config --local core.hooksPath .githooks
```

`core.hooksPath` はクローンごとの設定です。新しくクローンした場合も上記のコマンドを実行してください。
設定は `git config --get core.hooksPath` で確認できます。

## 入力待ち・返答の確認先を一押しで開く

「Orca → 確認先を開く」をキーに一つ配置してください。操作IDや個別ワークスペースの設定は不要です。OrcaのCLIと状態通知フックは有効にしてください。

- キーには次に開く対象、入力待ち/返答候補の理由、取得範囲の候補件数を表示します。長い名前は先頭と末尾を残して省略し、プロジェクトの略記と短い識別子を添えます。設定画面で完全名とパスを確認できます。
- 押すと表示していた作業場所を最新状態で照合して開き、次の候補へ進みます。初回は入力待ち優先、その後は返答候補も含めて一巡します。進行中と返答済みのAIが同居するワークスペースも返答候補に含めます。新しいワークスペースは自動追加します。
- 件数はワークスペース単位で、待ちと返答の同居は入力待ち1件として数えます。**未読数や残タスク数ではありません。開いても件数を減らさず、既読・承認・対応済みにはしません。** 状態が続けば一巡後に再び表示します。入力待ちには親AIへの待ちも含まれ得ます。
- 対象が消失したり状態・実行環境が変わった場合は、その押下で別候補を開きません。新表示を確認して再度押してください。候補なしの押下は再取得のみです。長押しに追加操作はなく、要求中の連打は溜めません。
- 「一部取得」「一部不明」は全体を確認できていない表示です。接続失敗をゼロ件や完了として扱いません。該当ペインを特定できない場合はワークスペースまで開くため、入力先はOrcaで確認してください。

既存の操作IDの選択は変更しません。たとえばこのキーでBを開いても、Aを選択中の「コマンド・AI指示」キーはAが対象のままです。「アクティブAIに入力」はOrcaで選択したペインが対象です。どちらも別途キーを押す必要があり、この確認先キーから入力・承認・コマンド実行は行いません。巡回位置と移動結果は再起動時にリセットされます。

調査と採用理由は [AI駆動開発の課題](docs/research/ai-development.md)、[設計](docs/design/attention-workflow.md) を参照してください。コードの正しさや仕事全体の完了は判定しません。

## ワークスペースの状態を表示する

Orca を起動し、Orca の設定で CLI とエージェントの状態通知フックを有効にしてください。キーとダイヤルに同じ「操作 ID」を設定して組み合わせます。

状態キー・コマンドキー・ダイヤルには、ワークスペース名の先頭と末尾を残す2行表示と、プロジェクトの略記・短タグを表示します。キー上段の `ID` は操作 ID、短タグは対象ワークスペースの照合補助です。設定画面には完全な名前・プロジェクト・パス・ワークスペースIDと同じ短タグを表示するので、同名の対象も照合できます。アクティブAI入力は操作IDに連動せず、画面選択への入力として区別します。

キー・ダイヤルの表示名は、Unicodeの正準同値（NFC）とASCII空白を揃えてから省略します。絵文字の書記素を分断せず、全角・半角を一律に変換しません。詳細画面の完全名・パス・IDと、実行する本文・宛先IDは元の値を保持します。

短タグには衝突の可能性があり、一意なIDや会話IDではありません。取得した一覧で短タグ・省略名・プロジェクト略記まで同じになる場合は「表示重複・要照合」と表示し、そのキーからは移動・実行しません。設定画面の完全IDとパスを確認し、Orca側で操作するか、見分けられるワークスペース名へ変更してください。検出範囲は取得できた一覧内です。接続失敗・対象消失ではプロジェクトを未取得と表示します。

1. 開発用リンクを設定済みなら `npm run build` と `npm run restart` を実行します。通常インストールの場合は `npm run pack` で作ったインストール用ファイルを開いて更新します。
2. Stream Deck の「Orca → ワークスペースの状態」を空いているキーに配置します。
3. 「Orca → ワークスペース切り替え」をダイヤルに配置します。
4. 最初だけ、それぞれの設定画面で操作 ID を合わせます。既定値は両方 `main` なので、そのままでも連動します。別の組には `sub` や `左上` など、別の ID を設定します。前後の空白は除き、大文字・小文字は区別します。
5. ダイヤルを回すと、同じ ID のキーに表示するワークスペースが切り替わります。左右どちらにも回せて、端で折り返します。回転だけでは Orca の画面は移動しません。
6. ダイヤルを押し込むと、現在位置の次から「入力待ち」のワークスペースだけを順送りし、同じ ID のキーに表示します。末尾では先頭に戻り、入力待ちがない場合や状態を取得できない場合は現在の選択を維持します。この操作も表示対象の切り替えだけを行います。
7. キーを押すと対象のワークスペースを開きます。明示的な入力待ちがあれば、そのターミナルを優先します。対応するターミナルがない場合はワークスペース自体を選択します。選択時のセッション復元は Orca の通常動作に従います。

ワークスペースは自動取得します。新しく作るたびに設定画面を開く必要はありません。ターミナルがないワークスペースも候補に含めます。候補はプロジェクト名・ワークスペース名の順で並び、ダイヤルのタッチストリップにも選択中の名前と位置を表示します。

同じ操作 ID を持つキーが複数ある場合は、全て同じ選択を表示します。複数のダイヤルにも同じ ID を設定できます。別々に選びたいキー・ダイヤルには異なる ID を使ってください。

進行中のキーは青い背景で白いインジケーターが回転します。ワークスペース名と状態はそのまま表示し、入力待ちなど他の状態になると静止表示に切り替えます。非表示のキーと接続失敗中のキーではアニメーションを止めます。

| 表示             | 意味                                                       |
| ---------------- | ---------------------------------------------------------- |
| 進行中           | 同じワークスペース内に実行中のエージェントがいる           |
| 入力待ち         | Orca が明示的な入力待ちを報告している（宛先はOrcaで確認）  |
| 返答あり・要確認 | 返答の終了、ブロック、中断などで内容の確認が必要           |
| 待機             | Orca が監視対象のエージェントを検出していない              |
| 状態不明         | 接続失敗、未取得、割り当て先の消失などで状態を確認できない |

選択は操作 ID ごとに保存し、プラグインの再起動後も復元します。一覧の並びが変わっても選択したワークスペースの ID を保持します。削除・アーカイブされた場合は状態不明になり、ダイヤルを回すと有効な候補に切り替わります。接続失敗中は古い候補を使って切り替えません。

監視対象は Orca が認識するエージェントです。同じワークスペース内の複数エージェントと、Orca が集約したサブエージェントの状態を利用します。別ワークスペースは別のキーで扱います。通常の文章で質問して返答を終えたケースは入力待ちとして検知できないことがあるため、「返答あり・要確認」も確認してください。仕事全体の完了判定は行いません。

状態は約2秒間隔に加え、ダイヤルの回転・押し込み時にも取得し、表示中のキーで監視を共有します。連続操作は取得中の通信を共有して入力順に反映します。更新中にキーを押した場合は、選択とキー表示の更新が終わってから対象を開きます。表示待ちは最大2秒で、待機中に選択・設定が変われば中止します。接続失敗時は前回の進行中表示を保持せず、状態不明にします。キー操作時には最新のターミナル一覧を取得し、Orca の再起動や設定変更で対象を確認できなくなった場合は警告を出します。入力や承認は開いた Orca 側で行ってください。

ページを切り替えた際は、最後の正常取得から5秒未満の情報があれば再取得中の表示に一時利用し、「状態不明」のちらつきを抑えます。再表示時には必ず最新情報を取り直し、失敗した場合は保持した情報も破棄して状態不明にします。保持データは新しい操作 ID への自動割り当てやダイヤル操作には使いません。初回表示や古い情報しかない場合は、取得完了まで状態不明になります。

CLI は環境変数 `ORCA_CLI_COMMAND`、PATH、macOS の `/opt/homebrew/bin`・`/usr/local/bin` から実行前に選びます。接続に失敗した CLI を別ビルドへ切り替えることはしません。
ネイティブ Chat やリモート環境は実機未検証です。ターミナルなしでのワークスペース選択は Orca 1.4.229 の認証済みローカル RPC `worktree.activate` を使用し、CLI で取得した runtimeId と一致する実行環境だけを操作します。接続先や切り替え結果を確認できない場合は操作を止めて警告します。

設定や割り当てを変更した直後など、対応するキー画像の送信がまだ終わっていない間は、その押下では移動・実行・入力を行いません。表示を確認して、もう一度押してください。遅れて画像が届いても自動で操作を再開しません。SDKへの画像送信完了は物理画面の描画完了を保証するものではありません。

## コマンドを実行・AIへ指示を送る

1. 「Orca → コマンド・AI指示」をキーに配置し、対象を選ぶダイヤルと同じ操作 ID を設定します。
2. 実行モード、ボタンの表示名、実行内容を入力して「保存」を押します。設定を保存しただけでは実行しません。
3. 実機のキーを押すと、同じ操作 ID で選択しているワークスペースに対して一度だけ実行・送信します。ダイヤルで一覧を更新中の場合は選択の確定を待ちます。

- **シェルコマンド**：`npm test` などを、そのワークスペースの新しい実行用ターミナルで起動して表示します。Orca が起動するシェルの文法で入力してください。既存の AI 端末へのコマンド入力は行いません。
- **AIへの指示**：「今回の変更をレビューして」などを、Orca CLI が認識するターミナル上の AI へ送ります。「AIが1つなら自動選択」は、送信可能な AI が1つの場合だけ送信します。複数いる場合は設定画面の送信先から選んでください。

シェルには「終了時にターミナルを閉じる（成功・失敗とも）」と「正常終了時だけターミナルを閉じる」の二つのチェック項目があります。既定は両方オフです。前者がオンなら終了コードにかかわらず閉じ、後者だけオンなら終了コード 0 の場合だけ閉じます。両方オンなら前者と同じ動きです。

自動クローズは macOS / Linux の `sh` と環境変数 `$SHELL` のシェル（未設定なら `/bin/sh`）で実行します。実行内容は別のシェルプロセスで動かすため、`exit` も含めて終了コードを取得できます。バックグラウンドへ切り離した処理ではなく、登録したスクリプト自体の終了を判定します。プラグインの稼働中に終了を監視し、この実行で作ったターミナルだけを閉じます。Orca やプラグインの再起動、端末の再作成、通信切断などで終了や対象を確認できない場合は自動では閉じません。直近の実行欄で終了コードと自動クローズの結果を確認できます。

指定した AI の送信先はワークスペースごとに保存します。送信時にワークスペース・runtimeId・端末の識別子・AIの種類を確認し、端末の再作成や種類の変更を検知した場合は送信せず選び直しを求めます。同じ端末内で同じ種類の AI が別の会話を始めたかは判別しません。AI がいない場合に新しい AI を起動することはありません。ネイティブ Chat への指示送信は対象外です。

ボタンは要求中の連打をまとめ、取得途中に設定や対象が変わった場合は実行前に中止します。「受付済み」はコマンドや指示の受付であり、処理の完了・テスト成功を表しません。AI の処理開始が確認できた場合は、設定画面の直近の結果に表示します。結果不明の場合は自動で再実行・再送信せず、設定画面に元のワークスペース名と結果を残します。実際の出力は Orca で確認してください。

## アクティブな AI に文字列を入力する

1. 「Orca → アクティブAIに入力」をキーに配置します。操作 ID やダイヤルの設定は不要です。
2. 入力する文字列と、必要ならボタンの表示名を設定して保存します。
3. 入力後に実行したい場合だけ「Enterも送る」をオンにします。既定はオフです。
4. Orca で対象の AI ターミナル・分割ペインを選択してから、実機のキーを押します。

同じワークスペースに AI が複数いても、選択中のペインだけへ入力します。シェル、ブラウザ、ファイル、ネイティブ Chat を選択している場合や、対象が消失・切断した場合は入力しません。別の AI に振り替えることもありません。入力の取得中に選択や設定が変わった場合は中止します。

既存の入力は消さずに追加入力します。「Enterも送る」をオンにした場合は、既存の入力も含めて送信します。オフの場合、改行・タブを含む文字列は bracketed paste として渡します。AI 側がこのペースト形式に対応している必要があります。受付結果は設定画面の「直近のキー操作」に表示し、不明な結果を自動で再送することはありません。

現在は macOS / Linux のローカル AI ターミナルが対象です。macOS 標準の `/usr/bin/sqlite3`、Linux は PATH 上の `sqlite3` を使います。Orca 1.4.229 のアクティブなプロファイルの SQLite 保存状態を読み取り専用で参照し、CLI の実行環境・画面の有無・入力先の AI を照合します。画面の切り替えがまだ保存状態に反映されていない瞬間は、以前の選択が取得される可能性があります。切り替え直後の連続操作にはこの制約があります。保存状態やランタイムを確認できない場合は入力しません。Windows、ネイティブ Chat、リモート環境は対象外です。

## プラグインのビルドとインストール

Stream Deck アプリ 6.9 以上と Stream Deck + が必要です。キーとダイヤルに対応しています。
SDK は `@elgato/streamdeck` 2.1.2、プラグイン内の実行環境は Node.js 20 を使用しています。

```sh
npm run build
npm run validate
npm run link
npm run restart
```

Stream Deck アプリのアクション一覧から「Orca → ワークスペースの状態」をキーに、「Orca → ワークスペース切り替え」をダイヤルに配置してください。対応付けは上の操作 ID の説明を参照してください。

`link` は開発用にこのリポジトリの `.sdPlugin` ディレクトリを Stream Deck にリンクします。

インストール用ファイルを作る場合は `npm run pack` を実行します。`dist/` に生成された `.streamDeckPlugin` ファイルをダブルクリックしてインストールできます。

- `src/plugin.ts`: SDK 接続とアクション登録。
- `src/actions/workspace-status.ts`: キーとダイヤルの操作。
- `com.tanaka-takuto.orca.sdPlugin/manifest.json`: プラグインの定義。
- `com.tanaka-takuto.orca.sdPlugin/imgs/`: Elgato CLI 付属のテンプレート画像。

SDK と開発用 CLI はプロジェクトの依存としてインストールしているため、グローバルインストールは不要です。
参考: [公式 SDK ドキュメント](https://docs.elgato.com/streamdeck/sdk/v2/guides/keys/)、[公式 CLI ドキュメント](https://docs.elgato.com/streamdeck/cli/commands/link/)。

## 保存時に自動反映する開発モード

初回のみ `npm run build` と `npm run link` を実行してください。`.streamDeckPlugin` ファイルから通常インストールした Orca がある場合は、先に Stream Deck アプリで Orca をアンインストールしてからリンクします。他のプラグインは操作しません。必要に応じて Orca のアクションを配置し直してください。

```sh
npm run dev
```

このコマンドを起動したまま `src/` を保存すると、自動ビルド後に Orca プラグインだけを再起動して反映します。manifest・画像・UI の変更も監視します。pack や再インストールは不要です。再起動時にはプラグインのメモリ上の状態がリセットされます。

ビルドと公式 CLI の検証が成功した場合だけ再起動します。構文エラーや不正な manifest がある場合は再起動せず、修正して保存すると再開します。型チェックは `npm run typecheck` で実行します。終了は `Ctrl+C` です。

開発用リンクを確認できない場合、`dev` は理由を表示して終了します。通常インストールしたコピーを誤って再起動して、変更が反映されたように見せることを防ぎます。

## Git フック

フックは `.githooks/` で管理します。

- `pre-commit`: `npm run lint` でプロジェクト全体の JavaScript・TypeScript・JSON などを Biome で lint・整形チェックします。エラーがある場合はコミットを拒否します。ステージしていない変更もチェック対象です。
- `commit-msg`: 自作の `.githooks/check-commit-message.mjs` で先頭行が [Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) 形式かを検証し、不正なメッセージを拒否します。検証スクリプトは Node.js の標準機能のみを使用し、commitlint などの追加ツールは使いません。

コミットメッセージの形式は `type(scope): 説明` です。`scope` は省略できます。破壊的変更は `feat(api)!: 説明` のように `!` を付けて示せます。

```text
feat: Orca のワークツリーを切り替えるアクションを追加
fix(dial): ダイヤルの回転方向を修正
chore: Git フックを設定
```

使用できる type は `build`、`chore`、`ci`、`docs`、`feat`、`fix`、`perf`、`refactor`、`revert`、`style`、`test` です。
type は小文字で指定し、コロンの後には半角スペースと空でない説明を書いてください。本文・フッターは検証対象外です。

## チェックと修正

```sh
npm run lint
npm run lint:fix
npm test
```

`lint:fix` は安全に自動修正できる lint エラーと整形を修正します。変更内容を確認し、`git add` してからコミットしてください。
