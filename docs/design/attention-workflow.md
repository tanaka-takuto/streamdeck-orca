# 確認先を開く

決定日: 2026-11-07。根拠: [AI駆動開発の課題](../research/ai-development.md)。独立UI/UX批評を経て採用した製品仕様。

## 解く範囲と選択

並列AIを順に開いて「どこに入力待ちや返答があるか」を探す負担を減らす。生成コードの正しさ、変更の理解、マージ可否は判定しない。既存ダイヤルは固定操作IDの対象を選ぶ役割を維持し、独立した「確認先を開く」キーを一つ置くだけで全ワークスペースの候補をたどれる。

既存押し込みの機能拡張は、入力待ち選択という合意済み契約とコマンドの宛先を曖昧にするため見送り。入力待ち・返答の専用2キーは次点だが初版は1枠の体験にする。通知の既読・非表示はエピソードの確実な識別や再出現が複雑で、開いたことを対応済みと誤認しやすいため見送る。通知音・強い点滅・自動送信・一括承認も加えない。代替案の比較は独立設計レビュー3節。

## 操作と観測

- 配置だけで自動取得する。操作IDや個別ワークスペースの割当不要。複数配置は同じ巡回位置を表示する。
- 入力待ちを報告したAIがあるWSを「入力待ち」、それ以外で返答終了またはブロックを報告したAIがあるWSを「返答候補」と数える。混在でも1WSを二重計上しない。進行中と返答の混在は返答候補として発見するが、全体完了とは呼ばない。親向けか人向けかは状態だけでは確定しない。
- 初回は入力待ち優先、同群はプロジェクト・名前・IDの安定順。更新だけで先頭へ戻さず、開いた後は両群を一巡する。新しい待ちは一覧へ自動追加し、次の巡回で到達する。緊急度順や未読順とは呼ばない。
- 短押しは**キー画像のSDK送信が完了した対象**のruntime、WS、host、理由、ペインと状態開始時刻を固定する。直前の再取得と移動処理自身の再取得の両方で照合する。不一致は別候補へ振り替えず、中止して新表示を見た次の押下を待つ。操作中の連打は溜めない。画像送信中で対象未確定なら再取得だけ行う。SDK送信完了は物理画面の描画完了を測った保証ではない。
- 対応する返答/待ちのペインを優先し、子の場合は親のターミナルへ戻る。対応端末がない場合はWSを開く。常に「作業場所を開く」という表現にとどめ、入力先はOrcaで確認して選ぶ。
- 成功したら巡回位置だけを進める。件数を減らさず、既読・承認・対応済みにしない。同じ状態なら一巡後に再訪する。失敗/結果不明では自動再実行しない。次の明示押下は改めて対象を確認してから開く。
- 候補なし/初回取得中の押下は再取得のみ。新たに見つかった対象を、その押下で開かない。長押しに追加操作はない。

## 情報と境界

キー144pxは理由、プロジェクト、先頭と末尾を残す対象名、押下ヒント、件数または観測範囲の警告。同名は安定した識別番号も併記し、設定画面で完全名・パスを確認できる。色に加えて文字で理由を示す。設定画面は設定欄を増やさず、現在の対象・取得範囲・直近の移動結果・操作説明を示す。

一部ホスト未取得・一覧打切りは「一部取得」、未知状態のWSがあれば「一部不明」。既知の候補を残しつつ、件数は取得範囲内であると説明する。失敗は「取得できません」でありゼロ件ではない。正常空・WSなし・AIなし・進行中ありを区別する。ページ切替の保持表示は5秒の既存制約に従い、候補の新設/変更に使わず、操作前には再取得する。

既存操作IDの選択と保存値は変更しない。新キーでBを開いた後も、Aを選択しているコマンドキーはAが宛先。一方、表示AI入力は保存選択を候補としてキーに表示済みのAIが対象となり、GUIの現在選択は保証しない。いずれも別の明示押下が必要。共通の移動世代ガードで、遅れた先行操作が後の移動を奪わない。

## 動作例

待ちA/B・進行中と返答が同居するCでは、3回の成功押下でA→B→Cを開き、候補件数は3のまま。Aの押下後にAが消失したり、新しい状態や実行環境に変わった場合は移動せず、Bへ振り替えない。

一部取得で候補0でも全件対応済みとは表示しない。既存mainがAのままCを開いても、コマンドの保存宛先Aは維持し、入力やコマンドを自動実行しない。
